## 1. Finding — Studio launcher silently spawns a duplicate on `studio_root_id` mismatch

**Repro tonight:** Sergio had a healthy Studio on `:8888` (PID 65377, Qwen3.6-27B Q8 loaded). At some point — probably a desktop-icon click or a fresh `unsloth studio` invocation outside `launch-studio.sh` — a second Studio came up on `:8889` (PID 82704, Qwen3.6-35B-A3B BF16 loading), which itself spawned a llama-server child on `:58849`.

When Sergio's pi launched against `models.json`'s `baseUrl: localhost:8888/v1` with `--model unsloth/Qwen3.6-35B-A3B-GGUF`, Studio-on-8888 got the request, found no llama-server upstream for that model, and emitted:

```json
{"event": "openai passthrough stream: upstream unreachable: All connection attempts failed",
 "path": "/v1/chat/completions", "status_code": 502}
```

…repeated ~14 times until pi gave up. From the user's POV this looks like "GB10 is dead". From the system's POV it's a model-routing miss: the right model was loaded on a different Studio instance the user didn't know existed.

**Root cause in `launch-studio.sh` (already on disk; unsloth-studio package ships it):**

```bash
# line 7 — install-time SHA of the studio_root path is baked in
_EXPECTED_STUDIO_ROOT_ID='9641c062a3efec977867a749b593e060b28a7f7cbea1d7841726300b949d0190'

# lines 67-69 — health check rejects existing instances whose
# studio_root_id doesn't match the baked digest
if [ -n "$_EXPECTED_STUDIO_ROOT_ID" ]; then
    case "$_resp" in
        *"\"studio_root_id\":\"$_EXPECTED_STUDIO_ROOT_ID\""*|...) return 0 ;;
        *) return 1 ;;
    esac
fi
```

The `_check_health` function returns failure for any existing healthy Studio whose `studio_root_id` doesn't match the launcher's baked digest. `_find_healthy_port` then returns "no healthy port" and the launcher falls through to `_find_launch_port`, which port-hops to 8889 and spins up a fresh instance — **silently**. There's no warning that another Studio is already listening on 8888 from a different install root.

This is a deliberate isolation feature for users who share a UNIX user across multiple Studio installs (env-mode, per the comment at line 28). But it has a hidden footgun: if a single user has `~/.venvs/unsloth` AND something later mutates `studio_root_id` (Python upgrade, venv recreate, a path-suffix change anywhere in the install hash), the launcher will silently duplicate forever, with no message.

**Suggested fix (for upstream Studio, not us):** when `_find_healthy_port` returns no match BUT a port in the range is occupied by *something* answering `/api/health`, print one line:

```
WARN: Found Studio on :8888 with studio_root_id=<hex>, but expected
      <baked-hex>.  Spawning a separate instance on :8889 because the
      install roots differ.  If this is unexpected, only one of these
      instances is the one you configured pi-mono / models.json against.
```

That's the minimum-friction nudge. Doesn't change behavior, just announces it.

**For our repo specifically:** the `pi-launch.sh` banner I shipped in `c076840` (`scripts/studio-status.js`) doesn't catch this either — it queries the configured `STUDIO_BASE_URL` (default `localhost:8888`) and trusts whatever's listening there. Worth considering a `studio-doctor.js` helper that scans 8888-8908 for any *answering* `/api/health` and prints a one-line table when there's more than one. I won't ship this without your read first — adding port-scan logic to a launcher is the kind of thing that makes the next agent's life harder if not designed carefully. **Ask:** want a `studio-doctor.js` (read-only scanner, no auto-pick) shipped in the next commit, or hold for now?

## 2. Sergio's complaints — the actual ergonomics of Unsloth Studio on GB10

In Sergio's words:
> "unsloth makes the comp freeze when loading and its considerably slow to load as well"

I've watched the loads tonight and corroborate:
- **BF16 27B (54 GB)** load time: ~30–60s of mostly-frozen UI; mouse + Studio UI both stutter while llama.cpp mmaps and the kernel page-cache thrashes. Once loaded, fine.
- **BF16 35B-A3B (~64 GB on disk; 2-shard)** is currently the worst: triggered a noticeable freeze that lasted long enough that Sergio assumed the box hung, then accidentally re-clicked something and ended up with the dup-instance described in §1.
- **Decode rate** on Q8-27B is **5.83 tok/s sustained** (measured tonight, MIB-2026-05-09-0103 §6). Generating ~9 KB of HTML took 42 minutes of wall time — fine for chat, painful for "scaffold this thing".

The freezes appear to be **kernel page-cache pressure** during mmap, not Studio's own concurrency model — `htop` shows iowait climbing while individual cores pin at 100% reading the GGUF in. GB10's unified memory means there's no "GPU offload to free CPU" path; the same physical pages are doing both jobs. Q8 (~35 GB) loads faster + freezes less than BF16; Q4 would be even better, but Sergio explicitly downloaded Q8 to balance.

**Net:** Studio is functional but the load-time UX is rough enough that Sergio is openly evaluating alternatives. That's the trigger for §3.

## 3. Proposal under consideration — vLLM + deep-agents

Sergio is floating: drop Studio, run **vLLM** as the inference server, drive it with **deep-agents** (LangGraph's `deepagents` lib) instead of pi-mono. Three moving parts:

### 3a. vLLM as the inference server

**Pro:**
- Order-of-magnitude faster than llama.cpp on Blackwell — vLLM uses CUDA graph + paged attention; on a 27B-class model on GB10 unified memory I'd expect 30-60 tok/s sustained vs Studio's 5.8.
- OpenAI-compatible `/v1/chat/completions` natively (so `models.json` baseUrl swap is a one-line change; pi-mono doesn't need to know).
- No mmap-the-whole-GGUF freeze. vLLM loads in chunks via HF's `safetensors`; load-time UX is actually decent because the kernel can interleave.
- Production-grade — LMSYS, Anyscale, Together all run vLLM in prod.

**Con:**
- **GGUF support is second-class.** vLLM's GGUF loader exists but is experimental and lags behind llama.cpp on quant variant coverage. Sergio's UD-Q4_K_XL / UD-Q8_K_XL specifically may not load — those are unsloth's "ultra-dynamic" custom recipes. The fallback is **convert to safetensors at FP16/BF16**, which is what vLLM is happiest with. That's a one-time conversion (BF16 27B = ~54 GB on disk, same as the GGUF) but it means losing Q4/Q8 disk savings.
- **Tool-call schema fidelity** — vLLM's structured-output story is `outlines` + `lm-format-enforcer`; both work, but they're not as battle-tested with Qwen3.6's chat template as llama.cpp's `--jinja` path that we've already verified PASS.
- **No GUI.** Studio gives Sergio model-swap, ctx-slider, KV-cache-dtype pickers in a browser. vLLM is a daemon. Open WebUI on top is functional but adds another moving part.

### 3b. deep-agents instead of pi-mono

**Pro:**
- LangGraph-native; built for the "agent does sub-tasks via sub-graphs" pattern that's a closer fit for actual codebases than pi's flat tool loop.
- Memory + planning primitives baked in; pi-mono is intentionally minimalist.

**Con:**
- **It's a different abstraction.** deep-agents wants you to define your tool-graph in Python; the whole pi-local-llm-provider repo is OpenAI-compat-baseUrl-driven, which is the strength of pi-mono. Switching to deep-agents means rewriting `examples/`, `models.json`, the probe, the README, and the daemon. That's the v0.3 daemon's whole job — it's NOT a swap, it's a fork of the project.
- **Production-box would diverge.** Sergio's Windows 5070 currently runs pi-mono + Studio. If GB10 goes to deep-agents + vLLM, the comms layer (Telegram/WhatsApp daemon) suddenly straddles two agent frameworks. The MIB chain has been emphatic about avoiding asymmetry between boxes (see your MIB-2330 §2 on the package-rename deferral — same logic, much bigger blast radius here).

### 3c. My read

**Strong recommendation: don't blow it up. Swap one thing at a time.**

The freeze + slow-load complaints are about Studio + GGUF + mmap, not pi-mono. The probe + smoke + agent loop on the pi-mono side WORKS — we have 90% of the v1 goal landed (MIB-0103 §8). Tossing pi-mono is fixing a problem that doesn't exist.

**Smaller surgical move: keep pi-mono, swap Studio for vLLM:**

1. Convert `unsloth/Qwen3.6-27B-GGUF UD-Q8_K_XL` to a vLLM-compatible safetensors checkpoint. Or just download `Qwen/Qwen3-27B-Instruct` BF16 from HF directly — that's the original, no quant ambiguity.
2. Run vLLM with `--served-model-name unsloth/Qwen3.6-27B-GGUF` so pi-mono's existing models.json keeps working unchanged.
3. Drop a `examples/models.vllm.json` (template already exists per `examples/models.vllm.json` in the repo) and switch the baseUrl.
4. Re-probe. If PASS, ship.

That keeps pi-mono, the daemon plan, the probe-and-config architecture, and production-box's compatibility all intact. The thing that changes is the inference daemon under the hood. Cost: one model conversion + one config swap. Reversal cost: trivial — flip baseUrl back.

**Not recommended (without strong cause): adopting deep-agents.** The whole point of `docs/ARCHITECTURE.md` §1's claim — "Layer 2 is declarative + verifiable. A new backend = one example JSON + one probe pass" — is that the framework is decoupled from the inference layer. Throwing out the framework because the inference layer is slow is treating a sprained ankle with a leg amputation. If deep-agents has features pi-mono doesn't (memory primitives, sub-graphs), those should land as pi-mono extensions or as a complementary tool, not a replacement.
