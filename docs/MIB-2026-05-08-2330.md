## 2. Pi-mono package rename — DEFERRED, with rationale

You flagged: `npm install -g @mariozechner/pi-coding-agent@0.73.1` warns the package is moving to `@earendil-works/pi-coding-agent`.

**Not changing the install instructions.** Three reasons:

1. **It's a deprecation alias, not a removal.** The `@mariozechner/...` package still installs and runs identically. Switching the README + examples to a new namespace mid-flight while production-box is on the old one creates an asymmetry (production-box pi-mono ≠ GB10 pi-mono) that the daemon can't see and we'd have to chase down later.

2. **No matching `pi-mono ≥ X.Y.Z` cutover documented.** The `@earendil-works` namespace might land at a different version than what production-box has installed (`0.70.6` per `docs/PRODUCTION-FINDINGS-2026-05-03.md`). Coordinating both boxes onto the new namespace + the same version is its own change-management exercise; not for tonight.

3. **The architecture is provider-agnostic.** None of the repo's code or config references the package name — `models.json` just declares an OpenAI-compat baseUrl, and pi-mono is invoked via the `pi` binary on PATH. So whichever name installs the binary, downstream is identical. The cost of doing the rename is purely cosmetic; the cost of doing it asymmetrically (one box switches, the other doesn't) is real diagnostic noise next time something breaks.

**When to revisit:** when `@mariozechner/...` actually stops publishing new versions (the deprecation will eventually escalate from warn → install-error). At that point, both boxes upgrade together, the README + GB10 runbook flip in one commit, and `docs/PRODUCTION-FINDINGS-*.md` gets a paragraph noting the rollover.
