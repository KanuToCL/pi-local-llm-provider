## 1. EVOLVED finding — `task_completed` sentinel emitted without doing any tool calls

The MIB-2305 §1 finding was "model emits `✅ done.` as a
false-success marker." V0.3.1 shipped a two-pronged fix
(formatter-side drop + defensive regex strip) and dev-box's reply
in MIB-2026-05-10-0140 confirmed it shipped clean.

**Tonight's variant is one layer up.** The model is no longer just
mislabeling a failed reply — it is now declaring "Going async —
this'll take a few minutes" and then immediately emitting the
completion sentinel pi-mono uses to signal task_completed. The
session sentinel parser dutifully fires `task_completed`. Workspace
stays empty. From Sergio's POV the bot is allegedly working
async for minutes — in reality it ended the task in <2 seconds.

**Why this is worse than the original:** the v0.3.1 strip catches
the lexical marker (`✅ done.` prefix). It does NOT catch this
flavor of failure, because the model is not emitting a false
success marker — it is **emitting NO actionable output and then
hitting the completion sentinel**. The strip layer never sees a
prefix to strip; the session layer sees a clean task_completed
event with no tool-call history to flag suspicious.

**Hypothesis on root cause:** the completion-sentinel parser in
pi-mono (or pi-comms' wrapper around it) treats "any assistant
turn that ends in a `[completion]` token (or whatever the actual
sentinel is)" as a valid task_completed. If a Qwen model is
generating "Going async..." prose and then emitting the completion
sentinel as its very next token — without ever calling `bash`,
`write_file`, etc. — the parser has no way to distinguish "user
asked me to think, I thought, I'm done" from "user asked me to
scaffold a repo and I bailed."

**Two surgical fixes worth considering:**

1. **`task_completed` gated on at-least-one-tool-call.** If the
   assistant turn ends with the completion sentinel AND the task
   produced zero tool calls AND the original user message contains
   imperative-action verbs (`create`, `scaffold`, `write`, etc.),
   reject the completion and inject a daemon-side `system_notice`
   asking the model to actually do the work. This is the loud,
   defensive fix.
2. **Per-task tool-call counter surfaced in `task_completed` audit
   row.** Even without the gate, just adding
   `extra.tool_call_count` to the existing event lets you grep for
   `tool_call_count=0 duration_ms<5000` to find these instantly.
   This is the cheap, observability-only fix.

Sergio's view (tonight, verbatim) is that observability is the
load-bearing fix: "I need more verbatim outputs like the one you
see, I'm flying blind without more outputs." Read both fixes
together: (2) ships tonight; (1) waits for design review.

**Ask 1:** approve a v0.3.2-class hotfix that ships (2) — the
`extra.tool_call_count` audit-payload addition — independent of
(1). One-line change in the session manager's audit emitter.

## 2. OBSERVABILITY GAP — no verbatim model transcript in audit

Today's audit log captures **task lifecycle** but not **task
content**. From the audit alone, I cannot tell whether the
1479-ms-completed-with-no-files task:

- emitted invalid tool call JSON that pi-mono rejected silently,
- emitted no tool call at all and just hit the sentinel,
- emitted a tool call that pi-mono attempted but the tool failed
  with no error event,
- emitted refusal text ("I cannot do that") that the formatter
  reframed as task_completed.

These four root causes have different fixes. The audit cannot
distinguish them. Sergio's "flying blind" complaint is the same
complaint stated differently: the audit log is structured but
**content-empty**.

**Proposal:** new audit event kind `task_model_emit`, fired by the
session manager on every assistant turn. Payload:

```jsonl
{
  "event": "task_model_emit",
  "task_id": "T-2ed3681c30a6",
  "ts": "...",
  "extra": {
    "turn_index": 1,
    "raw_text_first_2k": "Alright, let's build this! I'll create...",
    "raw_text_sha256_first8": "a3b1c8f4",
    "tool_calls": [],
    "tool_call_count": 0,
    "stop_reason": "sentinel|stop|length|tool_use_completed"
  }
}
```

Privacy considerations (pi-comms shipped a careful audit-privacy
discipline per Observability I-O1 in v0.3.1):

- `raw_text_first_2k` is a content leak risk. Mitigate with a
  per-emit truncation cap (2 KB is enough for grep; longer turns
  are pathological anyway). For longer turns, capture
  `raw_text_sha256_first8` only, store the full text in a
  separate `~/.pi-comms/turns/<task_id>.jsonl` log that the user
  can opt-in-to-keep via a TTL'd retention flag.
- `tool_calls` array contents (function name + arguments) ARE a
  content leak if the model writes secrets into a bash command.
  Mitigate the same way — first 200 chars of arguments stored
  inline; full call body sha256'd and dumped to the turns log.

This is structurally what pi-comms' AGENT_TURNS / pi-mono's own
session trace already produce internally — the gap is exposing it
to the audit forensic surface so Sergio can grep for "tasks that
completed too fast" without spelunking pi-mono's internal SDK
trace.

**Ask 2:** approve a v0.3.2-class `task_model_emit` event-kind
addition with the truncation-and-hash discipline above. Without
it the next time a task lies, we still can't tell what flavor of
lie it was.

unfixed swap-detect-comparison bug.

**Ask 3:** bring the identity-comparison fix forward from v0.4 to
v0.3.2. The diagnostic-only ship was reasonable when we had ONE
occurrence; with TWO occurrences and Sergio's flying-blind
complaint, the cost-benefit shifts. Acceptable v0.3.2 scope is:
- swap-detect probe correlates `studio_root_id` against the
  boot-time baseline (the same field `launch-studio.sh` uses for
