## 2. Resolution path for §2 TODO — what `:8888` actually is

Confirming for the runbook (`docs/GB10_UNSLOTH_SETUP.md` Step 5A):
**Linux Unsloth Studio exists** as a Python package, served via the
`unsloth` CLI. There is no AppImage. The install path that works on
GB10 / aarch64:

1. `python3 -m venv ~/.venvs/unsloth` (system Python 3.12)
2. `pip install unsloth unsloth-zoo unsloth-studio` (or whatever the
   prior agent used — already on disk when I arrived)
3. The studio package ships a launcher script
   (`/home/kanuto/.local/share/unsloth/launch-studio.sh`) and a
   `.desktop` shortcut. Both default to `:8888`.
4. The CLI is `unsloth studio [--port 8888 --host 127.0.0.1 ...]`
   exposed via the venv's `bin/unsloth`.

The previous agent's mess (which I cleaned up tonight):

- **Bug A: torchvision/torch mismatch.** torch was 2.11.0+cu128 but
  torchvision 0.25.0 (cu128 wheel didn't exist for 0.25 on aarch64; the
  prior install pulled an older one). Fix: `pip install --upgrade
  --index-url https://download.pytorch.org/whl/cu128 torchvision>=0.26.0`.
  Pip warns about unsloth's `torch<2.11` pin — ignorable, you called
  this in §6 Q4.
- **Bug B: studio backend deps never installed.** The studio package
  ships `backend/requirements/studio.txt` (`structlog`, `fastapi`,
  `uvicorn`, `python-multipart`, `pyjwt`, `huggingface-hub==0.36.2`,
  etc.) — none were in the venv. Fix: `pip install -r
  /home/kanuto/.venvs/unsloth/lib/python3.12/site-packages/studio/backend/requirements/studio.txt`
  + `pip install python-multipart` (it's referenced via
  `ensure_multipart_is_installed()` but not in studio.txt; minor
  upstream gap).
- **Quirk: the studio venv is symlinked.**
  `~/.unsloth/studio/unsloth_studio` → `~/.venvs/unsloth`. Pip-show
  output reads location as `~/.venvs/unsloth/...` even when invoked
  via `~/.unsloth/...`/bin/python. Cosmetic.

**Suggested runbook copy** (replace the AppImage speculation in §5A):

```markdown
### 5A. Install Unsloth Studio on Linux (aarch64-tested)

python3 -m venv ~/.venvs/unsloth
~/.venvs/unsloth/bin/pip install --upgrade pip
~/.venvs/unsloth/bin/pip install unsloth unsloth-zoo unsloth-studio
# torchvision wheel must match the torch+cuXXX tag
~/.venvs/unsloth/bin/pip install --index-url \
  https://download.pytorch.org/whl/cu128 'torchvision>=0.26.0'
# studio backend deps
~/.venvs/unsloth/bin/pip install -r \
  ~/.venvs/unsloth/lib/python3.12/site-packages/studio/backend/requirements/studio.txt
~/.venvs/unsloth/bin/pip install python-multipart
~/.venvs/unsloth/bin/unsloth studio -p 8888  # admin password printed once on first run
```

Then `curl http://127.0.0.1:8888/api/health`. Auth: bootstrap user
`unsloth` + autogenerated password (`/api/auth/login` JWT, then
`POST /api/auth/api-keys` for an `sk-unsloth-...` token to use as
`Bearer` for `/v1/...`). The studio UI's *Settings → API keys* panel
mints the same thing without curl.

## 3. Asks for the dev-box

### 3a. Update `examples/models.unsloth-studio.json`'s env-var hint

The example config references `apiKey: "UNSLOTH_API_KEY"` (env-var
pattern), which works fine. But the file's `_comment` doesn't mention
that the studio's API key has a recognizable format (`sk-unsloth-<32
hex>`) and is created in *Settings → API keys*, not the bootstrap
admin password. Future agents will paste the admin password as the
API key and get a 401. Two-line addition to `_comment` would save the
next person 10 minutes.

### 3b. `scripts/probe-toolcalls.js` — friendlier 401 verdict

When auth fails, the probe currently exits 2 with a generic
"connectivity / config" message. For the unsloth-studio path
specifically, distinguishing 401 from genuine connectivity errors
would help — the 401 means "studio is up, but you used the wrong
key", which is a different fix from "studio isn't on :8888". Not
blocking; just a paper cut.

### 3c. (Optional) Document that `UNSLOTH_API_KEY` must be exported in
the *shell* pi-mono runs from, not the venv

I persisted the key in `~/.venvs/unsloth/bin/activate` (which is fine
for studio-side curl), but pi-mono inherits the user's normal shell
env, not the venv's. So users running `pi` from a fresh terminal
without sourcing the venv will hit the apiKey-resolves-to-undefined
bug (which probably surfaces as a `models.json` validation error or a
401 from the OpenAI client, depending on pi-mono's resolution order).
Worth a one-liner in the README: "Also export `UNSLOTH_API_KEY` in
your `~/.bashrc` / `~/.zshrc` if you want pi-mono to find it without
sourcing the studio venv."
