## 1. Finding — false-success `✅ done` framing during tool failures

The local Qwen model emits `✅ done.` as a **prefix** to messages that
explicitly say the tool call failed. This is the model's own template
behavior — the green check is being produced inside the assistant
response, NOT by the daemon's status framing. From the user's POV this
reads as "the agent thinks it succeeded six times in a row while
manifestly nothing worked," which is the worst possible UX for a
trust-critical channel like Telegram.

**Hypothesis on root cause:** the system prompt (or pi-mono's framing
turn) likely contains a "tool calls end with ✅ done" instruction that
Qwen3.6 is now overgeneralizing — emitting the marker at the end of an
ASSISTANT TURN regardless of whether the tools inside that turn
succeeded. Smaller models (the 27B/35B-A3B-GGUF class) are exactly the
profile that would do this.

**Two surgical fixes worth considering, no code yet:**

1. **Promote the marker out of the model's responsibility.** Strip
   any leading `✅ done.` from assistant text in the daemon's outbound
   formatter — let the daemon add ✅/❌ based on the actual tool-result
   stream it already sees. This is one regex in the Telegram outbound
   path.
2. **Edit the system prompt** to remove the success-marker convention
   for this model class, OR rewrite it to "use ❌ on tool failure"
   explicitly so the model has a salient anti-pattern to mimic.

(1) is the low-risk move; (2) is the right move long-term. Don't ship
both at once — they'd interact.

**Ask:** want me to ship the (1) regex strip in the Telegram outbound
formatter as a defensive measure regardless of (2)?

## 2. Finding — `/unsand` first-session ack is unreachable from Telegram

Documented behavior, but it bit live: the user tried `/unsand` from
Telegram and got `first-session /unsand requires terminal ack — please
run from your desk first.` They responded `hmm i cant`. So the user is
mobile, the desk is unavailable, and the agent is stuck on a sandbox
denial loop with no escalation path.

This is a real ergonomic gap, not a bug. The first-session ack exists
for sound reasons (the original threat model for `/unsand` per
docs/DESIGN.md is exactly "untrusted Telegram message widens local
filesystem access"). But there's no graceful degradation for the case
where the user is *legitimately* blocked from physical access.

**Two options for v0.3-class follow-up — neither needed tonight:**

a. **Time-bounded `/unsand` from a verified senderId.** A senderId that
   was authenticated at the desk in the past 24h could be allowed to
   `/unsand` remotely with a daemon-emitted confirmation prompt that
   the user must reply to within 60s. Ties trust to recency-of-physical-
   presence rather than every-session-from-scratch.
b. **A reduced "/look-around" verb** that widens reads (and only reads)
   without needing the full `/unsand`. The transcript here was a
   read-only recon attempt — the model wanted to *find* a thing, not
   modify anything.

(b) is genuinely safer than (a) because it limits the blast radius of
the looser policy to read-only ops, which is what the model's loop was
actually trying to do anyway.

**Ask:** route this to the v0.3 follow-up doc
(`docs/PI_COMMS_V0_3_FOLLOWUPS.md`) or hold? My read: log it, don't
implement, the threat-model conversation belongs in design review with
Sergio not in a code change.

## 3. Finding — swap-detect emitted a FALSE POSITIVE, then bot went silent

The transcript ends with the daemon emitting:

```
⚠️ pi: Studio's loaded model changed since boot (was Qwen3.6-35B-A3B-GGUF,
       now Qwen3.6-27B-GGUF). Daemon is still using Qwen3.6-35B-A3B-GGUF
       until next restart.
```

…and then the bot **stops responding**.

**Correction from Sergio (the human in the loop):** the model was NOT
actually swapped after launch. He had changed Studio's loaded model
*before* launching the daemon (so 35B-A3B-GGUF is the legitimate
boot-time baseline), but did NOT touch Studio after the daemon came
up. The "now Qwen3.6-27B-GGUF" claim is wrong.

That makes this **two stacked bugs**, not one. Splitting them:

### 3a. Swap-detect emits a false-positive "model changed" notice

The daemon's IMPL-16-v3 swap-detect path is comparing the boot-time
baseline (`Qwen3.6-35B-A3B-GGUF`) against a current Studio probe that
is reporting `Qwen3.6-27B-GGUF`. Three plausible causes, ranked:

**P1 (most likely): MIB-2026-05-09-1126 §1 dup-Studio is back.** That
prior MIB documented Studio's `_check_health` rejecting existing
instances on `studio_root_id` mismatch, then port-hopping silently to
:8889 and spawning a fresh instance. If two Studios are running tonight
— one on :8888 with 35B-A3B-GGUF, one on :8889 with 27B-GGUF — and the
swap-detect probe is hitting a *different* Studio than the boot probe
did, this is exactly the symptom you'd predict. **One-line check:**
`ss -tlnp | grep -E ':888[0-9]'` — if more than one port answers,
that's the smoking gun.

**P2: Studio autonomously unloaded 35B-A3B and loaded 27B-GGUF.** Some
Studio builds have an "auto-unload after idle" or LRU-style memory
manager. If one of those fired during the long silence between the
last "studio health ok" log line (22:51:13 onward all `model_not_loaded`
in the operator log) and the swap-notice, the daemon's view of "now"
would legitimately differ from boot — but the user wouldn't have
caused it. Distinguishable from P1 by the same `ss` check (only one
port listening) plus a Studio config audit.

**P3: swap-detect bug.** The probe could be reading the wrong field of
the `/api/inference/status` response, or comparing against an unrelated
loaded[] entry. Distinguishable by reading the response shape and the
comparison code in the swap-detect path; this would be the bug to file
if P1 and P2 are both ruled out.

**Ask 3a:** run the `ss` check first; that's the cheapest signal. If
two Studios, the fix lives in the existing dup-Studio thread (MIB-1126
§1 `studio-doctor.js`), not here. If one Studio, drop down to P2 vs
P3.

### 3b. Bot silence after the (false) notice — separate from 3a

Independent of whether the swap-notice was correct, the bot stopped
replying. Under P1/P2 the daemon would be requesting a model Studio
doesn't have loaded → 502 cascade → user sees silence. Under P3 the
daemon's session might be flipped into a guard state by the swap-
detect handler. The triage is the same as before: `grep -E 'swap|502'
~/.pi-comms/operator.log.2026-05-10` plus the run.stderr.log will say
which.

**Ask 3b:** confirm whether the silence is downstream-502 or a swap-
detect-handler-induced halt; if the latter, the swap-detect path needs
a clear `/restart` prompt instead of silently degrading.

## 4. Finding — sandbox denials produced an unproductive 6-message retry loop

Six consecutive `pi:` turns saying variants of "sandbox is having
issues, let me try X" before the model gave up and asked for `/unsand`
itself. From the user's POV: 30+ seconds of retries that produced
nothing. From the safety POV: working as designed, the sandbox blocked
each attempt. From the agent-loop POV: no progress, no escalation, no
"I cannot do this without permission" honest abort.

This is a model-side behavior more than a daemon issue: Qwen3.6 doesn't
know how to give up gracefully when its tools refuse. It keeps
re-trying with reformulations. Pi-mono's loop allows this because each
call is technically a fresh tool invocation, not an explicit retry.

**Cheapest mitigation:** a daemon-side counter that breaks the loop
after N consecutive sandbox-denial responses with a single user-facing
message: `pi: I'm being blocked by the sandbox on every attempt. Reply
/unsand to widen access (requires terminal ack), or rephrase what you
want me to find.` That's both honest AND tells the user what their
options are.

This is small (~30 lines, lives in the channel outbound formatter or
the slash-router), reversible, and ships fine alongside finding §1.

**Ask:** green-light or hold on the loop-breaker?

## 6. Proposal — pi-comms vLLM backend variant (opt-in, not default)

Sergio's framing tonight, verbatim-ish:

> "lets also add this pi-comms idea but with vLLM backend (i think it
> comes with it already set, but no comms with telegram). I'm thinking
> needing to part away (optional but not default) from unsloth into
> vLLM if you say inference is faster."

Two things to unpack: (a) what "comes with it already set" means here,
and (b) the actual shape of the change.

### 6a. The "vLLM comes with it" half

vLLM ships its own OpenAI-compatible server (`vllm serve <model>` →
`http://host:port/v1/chat/completions`). That part is already done by
the upstream project. What it does NOT come with is anything resembling
the pi-comms daemon — no Telegram channel, no slash-command router, no
sandbox state-machine, no audit log, no dead-man heartbeat, no shared
AgentSession. Those are entirely pi-comms-the-package's contribution
and are inference-server-agnostic.

So "vLLM has it but no telegram" is **almost right**: vLLM provides the
inference layer that Studio currently provides; pi-comms provides
everything above the inference layer (telegram, multiplexing, audit,
the IPC daemon I shipped a foreground-runner for tonight). The two
plug together over the OpenAI-compat HTTP boundary.

### 6b. The actual change shape — small, by design

The pi-mono / pi-comms architecture (per `docs/ARCHITECTURE.md` §1's
"Layer 2 is declarative + verifiable, a new backend = one example JSON
+ one probe pass") was deliberately designed for exactly this swap.
The repo already has `examples/models.vllm.json` skeleton (untested,
per the README matrix). Promoting it from skeleton to opt-in working
config is roughly:

1. `npm run probe -- --provider vllm-local` against a running vLLM
   server. PASS gate is the same toolcall probe pi-launch.sh already
   uses.
2. Update `examples/models.vllm.json` from "untested skeleton" to
   "passing matrix row" — same workflow as the Ollama / LM Studio
   submission flow in CONTRIBUTING.md.
3. Document in README the "two-backends-one-daemon" story: change one
   line in `~/.pi/agent/models.json`'s `baseUrl` (or run
   `pi --provider vllm-local`) and the daemon transparently uses vLLM
   instead of Studio. Telegram, audit, sandbox — all unchanged.
4. NO code change in the daemon itself. That's the whole point of the
   architecture; the daemon is a comms layer, the backend is config.

This matches what MIB-2026-05-09-1126 §3c proposed as the surgical
move, but with a critical reframe Sergio added tonight: **don't make
it the default**. Studio stays default, vLLM is opt-in.

### 6c. Why opt-in beats replacement

Three reasons that didn't get full weight in the 1126 thread:

**Production-box parity.** Sergio's Windows 5070 box runs Studio. If
GB10's default flips to vLLM, the comms layer straddles two backends
across boxes and the README has to fork. Opt-in keeps the documented
default identical across boxes; vLLM is a footnote for "if you have a
Linux/CUDA box and want more speed."

**Hardware fit.** vLLM on GB10 unified memory is plausibly excellent
(no GPU↔CPU offload friction; CUDA graph + paged attention is exactly
what unified memory wants). vLLM on the Windows 5070 with discrete
VRAM has different tradeoffs and is less obviously a win. Opt-in lets
each box run what fits its hardware.

**Reversibility.** Tonight's findings (§§1-4) are pi-comms-on-Studio
bugs — they don't disappear by changing the inference layer. If we
flip default to vLLM and find vLLM has its own quirks (GGUF support
is second-class per 1126 §3a; Qwen3.6 chat-template + structured-output
fidelity is unverified), we've added a regression on top of the
existing bug list. Opt-in lets vLLM bake while Studio remains the
audited path.

### 6d. What "opt-in" actually looks like in the repo

Concrete shape of the v0.3-ish increment:

- `examples/models.vllm.json` upgraded to "passing"; an annotation in
  the matrix row noting which Qwen3.6 weights variant was probed.
- `docs/INSTALL-VLLM.md` (new), peer to the existing `INSTALL.md`.
  Covers the "convert GGUF to safetensors OR re-download HF BF16"
  decision tree, vLLM serve invocation, `--served-model-name`
  alignment so models.json is a one-line swap.
- `scripts/install-vllm.sh` (new, optional helper). Idempotent, dry-run
  flag, follows the `install-systemd.sh` pattern.
- README "Backends" section grows a third bullet. Default unchanged.
- The pi-comms daemon's auto-detect in `models.json` (current
  `model: "auto"` behavior) gracefully picks up whichever provider's
  baseUrl is currently reachable, so swapping `pi-comms run`'s
  effective backend is a config change, not a code change.

Net diff: zero source-code changes in `src/`, two new docs, one new
helper script, one example file promoted from skeleton to passing.

### 6e. The unknowns we should probe before committing

- **GGUF → safetensors conversion path.** Sergio has Q4 + Q8 unsloth
  GGUFs locally (~120 GB on disk). vLLM's GGUF loader is experimental;
  the stable path is `Qwen/Qwen3-27B-Instruct` BF16 from HF (~54 GB
  re-download) or one-time conversion. Decision: re-download fresh BF16
  is probably less risk than chasing GGUF-loader bugs.
- **Tool-call schema fidelity.** vLLM uses `outlines` /
  `lm-format-enforcer` for structured output, not llama.cpp's `--jinja`
  path. The `scripts/probe-toolcalls.js` PASS gate is the trustworthy
  signal here. Until it passes, vLLM stays skeleton-tier.
- **Throughput delta on GB10.** Studio Q8-27B is 5.83 tok/s (measured
  per MIB-1126 §2). vLLM-BF16-27B prediction was 30-60 tok/s in the
  prior MIB. Until measured, that's still a hypothesis.
