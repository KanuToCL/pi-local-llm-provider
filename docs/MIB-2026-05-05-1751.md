## 4. Finding 1: GrammY long-poll silent hang (new, orthogonal)

After session 1's last task (T-c4f1a806bd3a, 17:18:51 UTC), Sergio sent further messages that were never received. The daemon stayed alive (PID 14016, 168MB, `task-state = idle`) but GrammY stopped delivering Telegram updates. The hang resolved on daemon restart.

**Audit evidence for session 1:**
```jsonl
{"ts":"2026-05-05T00:18:51.795Z","event":"task_completed","task_id":"T-c4f1a806bd3a","duration_ms":275}
// gap — no new telegram_inbound ever
{"ts":"2026-05-05T00:20:27.323Z","event":"pi_stuck_suspected","extra":{"stale_source":"telegram-poll","age_ms_telegram_poll":95807,"age_ms_pi_ping":93353}}
{"ts":"2026-05-05T00:21:57.339Z","event":"pi_stuck_suspected","extra":{"stale_source":"telegram-poll","age_ms_telegram_poll":185823}}
```

**Key diagnostic facts:**
- `telegram_connect` at boot (once), **never followed by `telegram_polling_error` or `telegram_disconnect`**. GrammY's `bot.start()` Promise did NOT settle — no error path was reached.
- `telegram-poll` went stale at 95s after last inbound. `pi-ping` went stale at 93s after last pi-mono event. Both are EXPECTED idle-staleness (no tasks = no pi-mono events; no messages = no onPoll calls) — not event-loop freeze.
- The event loop was NOT blocked. Bash tool uses async `spawn()` (verified: `src/sandbox/exec.ts:308`). Pi-ping / telegram-poll staleness is consistent with genuine idle.

**What we know for certain:**
- `bot.start()` never rejected (no error path hit, no `telegram_polling_error`)
- The daemon process was alive and healthy — not crashed, not OOM
- The event loop was not blocked (async `spawn()` confirmed at `src/sandbox/exec.ts:308`)
- The hang resolved cleanly on daemon restart

**What we don't know:** whether GrammY's poll loop was waiting on a dead socket, in an internal retry backoff, or simply never got pinged by Telegram after a server-side drop. We cannot tell from the current audit surface.

**Candidate root causes (ranked by best guess, not confirmed):**

**H1 — TCP-layer silent hang (top candidate):** GrammY's `getUpdates` HTTP connection went stale (NAT idle timeout / Windows TCP keepalive interval), but GrammY's HTTP client had no TCP-level read timeout. The poll is suspended waiting for a response that will never arrive. `bot.start()` doesn't reject because no error was surfaced — the socket just stopped sending data. This is the most common cause of "Telegram bot silently stops receiving" in Node.js long-poll bots, and explains why a restart fixes it (new TCP connection).

**H2 — GrammY internal exponential backoff:** GrammY has its own retry logic (grammy-runner / long-polling restart). If it encountered a transient error (network blip, 429, server close) that it classified as recoverable, it enters exponential backoff and retries silently — without rejecting `bot.start()`. The backoff window could be several minutes at high retry counts, which looks identical to a hang. Correlates with the 6-bash-call session causing a brief CPU/network spike that might have tripped a transient error.

**H3 — Telegram server-side update suppression:** Telegram's anti-flood mechanism occasionally stops delivering updates to a bot temporarily (without an explicit error response) if it detects high activity from the same account. The bot's `getUpdates` calls return empty repeatedly or time out server-side, and GrammY's poll loop keeps calling but gets nothing. From our side: poll appears healthy, no error, just silence. Restart forces a new session negotiation which may clear it.

**H4 — Node.js HTTP agent pool state after heavy I/O:** The 6 bash calls + file I/O may have left Node.js's underlying HTTP connection pool in a state where the pooled socket for the Telegram API connection was stale or mismarked. GrammY reuses the existing socket rather than opening a fresh one, and the reused socket is dead. This would also explain the correlation with the coding task specifically.

**H5 — Windows-specific TCP behavior:** Windows handles TCP idle timeouts differently from Linux/macOS. The Telegram long-poll uses a 30–50s server-side timeout. On Windows, if the OS-level TCP keep-alive doesn't fire in time (default Windows keep-alive interval is 2 hours), an idle long-poll connection can silently die at the socket layer without Node.js being notified. Less likely to be Windows-specific since bot works fine otherwise, but worth noting.

**Correlation note:** The hang followed immediately after T-89e465c8072b's 6 bash calls + T-c4f1a806bd3a's 275ms reply. Causation is unconfirmed — it may simply be that the Telegram long-poll TCP connection happened to expire during that window (idle timer fires regardless of what else the daemon is doing). The 6-bash-call session is suspicious but not proven causal.

**Design gap (`src/channels/telegram.ts:319-334`):**

```typescript
this.startPromise = this.bot.start().catch((error) => {
  // only fires if bot.start() rejects — silent hangs never reach here
  this.operatorLogger?.error("telegram_polling_error", ...);
  this.connected = false;
});
```

Under H1/H3/H4 the catch never fires. Under H2 GrammY handles the error internally before propagating. Either way: the daemon has no mechanism to detect a hung or silently-stalled poll loop and restart it.

**Suggested fix for v0.3 (addresses all hypotheses):**
1. Add a poll-attempt heartbeat (fires on every `getUpdates` call, not just update receipt) — makes H1/H2/H3/H4 all detectable via staleness.
2. Add a watchdog in `TelegramChannel` that calls `bot.stop()` + `bot.start()` when `age_ms_telegram_poll_attempt > threshold` while `this.connected === true`. Self-healing regardless of root cause.
3. Consider `bot.start({ timeout: 30 })` to force GrammY to re-raise on long-poll stall at the application layer (addresses H1 specifically).

## 5. Finding 2: `onPoll` heartbeat fires on update receipt, not poll attempt

Current: `telegram-poll` heartbeat fires only when a Telegram update is received (`src/channels/telegram.ts:116-126`). In a healthy but quiet daemon (no messages for 90+ seconds), `telegram-poll` goes stale and trips `pi_stuck_suspected`. This is a false positive.

Pre-v0.2.2, this was masked: `pi-ping` went stale even faster (tasks completed in 7ms → no pi-mono events). Post-v0.2.2, `pi-ping` now correctly stays alive throughout real inference, but the poll alarm still fires on silence.

**Audit comparison:**

| | Old (v0.2.1) | New (v0.2.2) |
|---|---|---|
| `stale_source` | `pi-ping` | `telegram-poll` |
| Why pi-ping stale | Task completed in 7ms, pi-mono actually still inferring | Task genuinely complete; pi-mono idle |
| Why telegram-poll stale | No messages | No messages (same) |
| Alarm valid? | Yes — pi-ping stale while model running = real stuck | **Ambiguous** — could be idle OR GrammY hung |

The fix is the same as §4 item 3: fire a `telegram-poll-attempt` heartbeat on each `getUpdates` attempt regardless of whether an update arrives.

## 6. Finding 3: Windows bash-tool cmd.exe semantic mismatch

During T-89e465c8072b, the model ran (inferred from artifacts):
```bash
mkdir -p "D:\Cosas\04_code\monorepo\butterfly"
```

On `cmd.exe /d /s /c mkdir -p "D:\..."`, Windows mkdir has no `-p` flag. cmd.exe created a directory literally named `-p` inside the workspace cwd (`~/.pi-comms/workspace/-p/`). The actual target path may have been created via a separate command or retry.

The HTML file `D:\Cosas\04_code\monorepo\butterfly\index.html` WAS successfully written (absolute path, unsandboxed on Windows). The spurious `~/.pi-comms/workspace/-p/` directory has been purged.

**The model doesn't know it's on Windows.** The system prompt (or `prompts/coding-agent.v2.txt`) has no OS context. The model defaults to POSIX assumptions: `mkdir -p`, `cat`, `grep`, `/` path separators, `sh` syntax.

**Suggested fix for v0.3:** Add to the system prompt or boot caveat:
> "You are running on Windows. Use `mkdir` without `-p` (Windows mkdir creates parent dirs automatically). Use `type` instead of `cat`. Use backslashes in paths or quote paths with forward slashes. The shell is `cmd.exe`."

Alternatively: translate common POSIX commands to Windows equivalents in the bash wrapper before exec. The classifier regex already examines commands — a pre-exec normalizer could rewrite `mkdir -p foo` → `mkdir foo` on win32.
