## 4. Finding 1: GrammY long-poll silent hang (new, orthogonal)

**Two confirmed incidents.** Session 1 (17:18 UTC) and session 2 (22:17 UTC) both exhibit the same pattern: bash-heavy task completes → GrammY stops delivering updates → `pi_stuck_suspected` fires → daemon alive but silent → restart resolves.

A third event at 22:13 UTC was a **confirmed false positive** — GrammY was healthy, just no messages sent for 114s. When the next message arrived at 22:15, `pi heartbeat from=dead to=healthy` immediately fired and processing resumed normally. This gives a clean way to distinguish: false positive self-recovers on next inbound; real hang does not.

**Full incident table:**

| Event | Time (UTC) | Bash calls before hang | Outcome |
|---|---|---|---|
| False positive | 22:13:14 | 0 (quiet gap after smoke 2) | Self-recovered at 22:15:44 |
| Incident 1 | 00:20:27 | 6 (T-89e465c8072b) | Daemon restart required |
| Incident 2 | 05:19:14 | 13 (T-f1a4f080a81f) | Daemon restart required |

**Bash-call counts are the only differentiator between the confirmed hangs and the false positive.** Zero bash calls → false positive. 6+ bash calls → real hang. This is now the primary correlating signal, not general daemon activity level.

**Audit evidence — incident 2:**
```jsonl
{"ts":"2026-05-05T05:17:42.695Z","event":"task_completed","task_id":"T-f1a4f080a81f","duration_ms":12623}
// gap — no new telegram_inbound despite messages sent
{"ts":"2026-05-05T05:19:14.772Z","event":"pi_stuck_suspected","extra":{"stale_source":"telegram-poll","oldest_age_ms":104704,"age_ms_telegram_poll":104704,"age_ms_pi_ping":90523}}
```

**What we know for certain:**
- `bot.start()` never rejected (no `telegram_polling_error` or `telegram_disconnect` in either incident)
- The daemon process was alive and healthy both times — not crashed, not OOM, `task-state = idle`
- The event loop was NOT blocked (async `spawn()` confirmed at `src/sandbox/exec.ts:308`)
- Both hangs resolved cleanly on restart
- The false positive self-recovered without restart, confirming GrammY was still polling

**What we don't know:** the exact mechanism by which rapid cmd.exe spawning disrupts the GrammY poll. Cannot determine from current audit surface alone.

**Candidate root causes (ranked — bash-call correlation now the primary signal):**

**H1 — Windows socket handle inheritance by spawned cmd.exe processes (NEW top candidate):** On Windows, `spawn()` with `stdio: ['ignore', 'pipe', 'pipe']` controls stdin/stdout/stderr, but does NOT prevent inheritance of other open handles including TCP sockets. When 6–13 `cmd.exe` processes are spawned rapidly, they may inherit the parent's open socket to Telegram's API. When those processes exit, the socket's reference count in Windows's handle table may be decremented incorrectly, leaving the socket in an undefined state from the parent's perspective. GrammY's poll loop then tries to read from a socket that Windows considers partially or fully closed — but no Node.js error event fires because the socket was still technically "open" from Node's view at the time of the `getUpdates` call. Restart opens a fresh TCP connection, bypassing the corrupted handle.

**H2 — libuv IOCP thread pool saturation (new):** Windows async I/O uses I/O Completion Ports. Spawning 13 child processes in 12 seconds creates 26 stdout/stderr named pipes, each requiring IOCP completion events for data and close. If libuv's thread pool is saturated processing these completion events, HTTP network I/O (GrammY's `getUpdates`) gets queued behind the pipe events. By the time the thread pool drains, the Telegram API server-side long-poll has timed out and closed the connection from its end — silently from Node's perspective.

**H3 — TCP-layer silent hang:** GrammY's `getUpdates` HTTP connection went stale (NAT idle timeout / Windows TCP keepalive interval) during the busy bash-call window. GrammY's HTTP client had no TCP-level read timeout, so it suspends waiting for a response that will never arrive. `bot.start()` doesn't reject because no error propagates from the socket layer. The bash-call correlation would be coincidental timing — the TCP connection expired during the I/O-heavy period. Less convincing now that we have two incidents at different times of day.

**H4 — GrammY internal exponential backoff:** If GrammY encountered a transient HTTP error (429, server close, timeout) during the bash-call window and classified it as recoverable, it enters exponential backoff and retries silently without rejecting `bot.start()`. With 13 bash calls in 12 seconds, a brief CPU spike could have caused a timeout that triggered backoff. The backoff window at high retry counts could be several minutes, matching the observed silent period.

**H5 — Node.js HTTP agent connection pool corruption:** Rapid spawn + pipe operations may leave Node.js's HTTP agent's connection pool with a stale or mismarked socket for Telegram's API. GrammY reuses the existing pooled socket, which is dead, rather than opening a fresh connection. No error fires because Node's socket object still appears valid.

**H6 — Telegram server-side anti-flood:** Telegram temporarily stops delivering updates to bots it perceives as high-traffic without sending an explicit error. The model running `git log`, `git status`, etc. generates many API responses — combined with the rapid bash-call activity, Telegram may have throttled updates server-side. GrammY's `getUpdates` continues but returns empty. From our side: poll appears healthy but silent.

**Correlation summary:** H1 and H2 are the strongest candidates because they directly involve Windows subprocess mechanics and are mechanically triggered by the bash-call count. H3/H4/H5/H6 could explain either incident independently but don't cleanly explain the bash-call correlation without additional coincidence.

**Design gap (`src/channels/telegram.ts:319-334`):**

```typescript
this.startPromise = this.bot.start().catch((error) => {
  // only fires if bot.start() rejects — silent hangs never reach here
  this.operatorLogger?.error("telegram_polling_error", ...);
  this.connected = false;
});
```

Under H1/H2/H3/H5 the catch never fires. Under H4 GrammY handles the error internally before propagating. Either way: the daemon has no mechanism to detect a hung or silently-stalled poll loop and restart it.

**Suggested fix for v0.3 (addresses all hypotheses):**
1. **Poll-attempt heartbeat** — fire on every `getUpdates` call attempt, not just on update receipt. Makes all 6 hypotheses detectable via staleness.
2. **Self-healing watchdog** in `TelegramChannel` — when `age_ms_telegram_poll_attempt > threshold` while `this.connected === true`, call `bot.stop()` + `bot.start()`. Resolves without daemon restart regardless of root cause.
3. **`bot.start({ timeout: 30 })`** — forces GrammY to re-raise if `getUpdates` doesn't return within 30s (addresses H3 and partially H4).
4. **Investigate Windows handle inheritance** — add `{ windowsHide: true, detached: false }` options already present; investigate whether `stdio` configuration fully prevents socket fd inheritance on Windows, or whether explicit `HANDLE_FLAG_INHERIT=false` is needed via native addon (addresses H1 specifically).

## 5. Finding 2: `onPoll` heartbeat fires on update receipt, not poll attempt

Current: `telegram-poll` heartbeat fires only when a Telegram update is received (`src/channels/telegram.ts:116-126`). In a healthy but quiet daemon (no messages for 90+ seconds), `telegram-poll` goes stale and trips `pi_stuck_suspected`. This is a false positive — **now confirmed empirically**.

At 22:13:14 UTC, `pi_stuck_suspected from=healthy to=degraded` fired with `stale_source=telegram-poll oldest_age_ms=114735`. No messages had been sent for ~114s after smoke 2. At 22:15:44, the next inbound message arrived and immediately triggered `pi heartbeat from=dead to=healthy` — GrammY had been polling the whole time, just receiving nothing. The alarm was a false positive.

Pre-v0.2.2, this was masked: `pi-ping` went stale in ~7ms (tasks completed immediately → no pi-mono events). Post-v0.2.2, `pi-ping` correctly stays alive throughout real inference, but the poll alarm now surfaces on legitimate silence.

**Audit comparison:**

| | Old (v0.2.1) | New (v0.2.2) |
|---|---|---|
| `stale_source` | `pi-ping` | `telegram-poll` |
| Why pi-ping stale | Task completed in 7ms, pi-mono actually still inferring | Task genuinely complete; pi-mono idle |
| Why telegram-poll stale | No messages | No messages (same) |
| Alarm valid? | Yes — pi-ping stale while model running = real stuck | **Ambiguous** — idle OR GrammY hung (cannot distinguish without poll-attempt heartbeat) |

The confirmed false positive also gives us the distinguishing signature: a false positive self-recovers with `pi heartbeat from=dead to=healthy` on the next inbound. A real hang (§4) produces no `pi heartbeat` recovery — messages sent go unheard. This is a useful post-hoc diagnostic signal, but it requires a message to arrive to tell the difference, which means operators have no way to pre-emptively detect real hangs.

The fix is the same as §4 item 1: fire a `telegram-poll-attempt` heartbeat on each `getUpdates` call regardless of whether an update arrives.

## 6. Finding 3: Windows bash-tool cmd.exe semantic mismatch

During T-89e465c8072b, the model ran (inferred from artifacts):
```bash
mkdir -p "D:\Cosas\04_code\monorepo\butterfly"
```

On `cmd.exe /d /s /c mkdir -p "D:\..."`, Windows mkdir has no `-p` flag. cmd.exe created a directory literally named `-p` inside the workspace cwd (`~/.pi-comms/workspace/-p/`). The actual target path may have been created via a separate command or retry.

The HTML file `D:\Cosas\04_code\monorepo\butterfly\index.html` WAS successfully written (absolute path, unsandboxed on Windows). The spurious `~/.pi-comms/workspace/-p/` directory has been purged.

**The model doesn't know it's on Windows.** The system prompt (or `prompts/coding-agent.v2.txt`) has no OS context. The model defaults to POSIX assumptions: `mkdir -p`, `cat`, `grep`, `/` path separators, `sh` syntax.

**Suggested fix for v0.3:** Add to the system prompt or boot caveat:
> "You are running on Windows. Use `mkdir` without `-p` (Windows mkdir creates parent dirs automatically). Use `type` instead of `cat`. Use backslashes in paths or quote paths with forward slashes. The shell is `cmd.exe`."

Alternatively: translate common POSIX commands to Windows equivalents in the bash wrapper before exec. The classifier regex already examines commands — a pre-exec normalizer could rewrite `mkdir -p foo` → `mkdir foo` on win32.
