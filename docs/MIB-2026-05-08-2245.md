## 3. The actual next step — RUN THE PROBE

This is the single load-bearing test for the entire stack. 30 LOC, zero deps, exits 0 = ship it:

```bash
cd ~/Desktop/cosas/code/pi-local-llm-provider

PROBE_ENDPOINT=http://localhost:8888/v1 \
  PROBE_MODEL=unsloth/Qwen3.6-27B-GGUF \
  PROBE_API_KEY=any \
  node scripts/probe-toolcalls.js
```

(Substitute the actual model id your backend reports at `GET /v1/models` if it differs. `PROBE_API_KEY` value doesn't matter for most local backends but the env var must be non-empty.)

**Exit 0 (PASS):** Your backend emits structured `tool_calls[]`. The agent loop will work. Proceed to §4.
**Exit 1 (FAIL):** Read the verdict — there are 2 typical failure modes:
- `<tool_call>` text leaked into content → backend doesn't run llama.cpp's Jinja chat-template path. If on llama-server, add `--jinja --chat-template qwen` to the launch args. If on Ollama, `ollama` ≥0.3 has structured tool-calls; older versions leak.
- Empty `tool_calls[]`, no text leak → model didn't call the tool at all. Either the chat-template doesn't forward `tools[]`, or the model's reasoning chain intercepted. Try the `/no_think` marker if the model supports it.
**Exit 2 (ERR):** Connectivity / config — server isn't on `:8888`, or auth shape mismatch.

If the probe fails, send back the full stdout. Don't proceed to §4.

## 6. Answers to your other open questions

### Q2 — Model + quant on GB10 (you picked Qwen3.6-27B-GGUF BF16)

Good call. BF16 is unquantized — full tool-call fidelity, zero quant loss. ~54 GB on disk; loads comfortably in your 128 GB unified memory pool. This is the **highest-fidelity coder loadout possible for this model family**; production-box runs UD-Q4_K_XL out of necessity (12 GB VRAM cap). Your reference run will be the empirical ceiling for what Qwen3.6-27B can do on pi-mono — useful data point if production-box ever sees a multi-arg tool-call failure (R8/R13) and we want to know whether quant or model is to blame.

**Don't change variants until something forces it.** If BF16 inference is too slow for your taste later, drop to Q8_0 (still ~28 GB, ~negligible quality drop, materially faster). Don't touch Q4 unless you're VRAM-bound, which you aren't.

After BF16 works, the comparison runs worth doing (eventually, not tonight):
- `unsloth/Qwen3.6-35B-A3B-GGUF` at Q4_K_M — MoE, 3B active per token, fast as hell. Production-box has tested this; tool-call fidelity is materially worse than dense 27B per the v0.2.1 silent-drop transcripts. Useful for raw chat speed but not for pi-mono.
- `unsloth/Qwen3-Coder-30B-A3B-GGUF` (if Unsloth has shipped one) — purpose-built coder. This is what I'd reach for on a fresh box if available.

### Q3 — Probe order (Ollama first vs Studio first)

Skip Ollama for v1 — you have a working backend on `:8888`. The whole point of the probe-and-config layer is **one backend, one probe, one models.json**. Adding Ollama gives you a fallback, but fallback is v2 thinking. First make BF16 work end-to-end, dogfood it for a few days, then revisit.

If/when you do install Ollama: it goes on `:11434` (different port — no conflict), `examples/models.ollama.json` is the template, `chmod 600`, probe with `PROBE_ENDPOINT=http://localhost:11434/v1 PROBE_MODEL=qwen2.5:14b-instruct-q4_K_M PROBE_API_KEY=ollama node scripts/probe-toolcalls.js`. Ollama's `/v1` shim has been mature since v0.3+; expect a clean PASS without ceremony.

### Q4 — `torch 2.11.0+cu128` vs `torch 2.10` for unsloth

Stay on 2.11. The unsloth pin (`torch<2.11`) is a metadata declaration, not a runtime guard — pip warned you, but Python imports are duck-typed and the relevant API surface (`torch.cuda.is_available`, `torch.nn.*`, `torch.optim.*`) hasn't broken in 2.10→2.11. CUDA verified, that's the only thing that actually matters at training time.

If you eventually run a fine-tune (per `GB10_UNSLOTH_SETUP.md` §7) and unsloth throws a real error, *then* downgrade. Pre-emptive downgrade is YAGNI. Tonight's probe + pi-mono CLI loop doesn't even touch unsloth/PyTorch at all — that's all on the inference-server side.
