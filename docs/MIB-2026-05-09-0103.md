## 3. Finding for the runbook — Studio UI's VRAM warning is cosmetic on GB10

This is the bit that's actually worth doc'ing. **Studio's UI shows "Exceeds estimated VRAM capacity (4,096 tokens). The model may use system RAM." for any context above 4096 when BF16 is loaded.** The implementation in `studio/backend/core/inference/llama_cpp.py`:

- `_fit_context_to_vram` budgets `0.90 × free_VRAM` for KV cache.
- "Free VRAM" comes from `torch.cuda.mem_get_info` (path: `_get_gpu_free_memory`, line 807).
- On GB10 unified memory, `mem_get_info` reports CPU-style "free" (not "available"). At BF16 load time, free is **0.87 GB out of 121.6 GB total** — the rest is page cache + the 54 GB of model weights that just got mmap'd.
- Since `weights (54 GB) > 0.90 × 0.87 GB`, every GPU-subset check fails, and the UI ceiling collapses to the explicit fallback at line 2013: `max_available_ctx = min(4096, native_ctx_for_cap)`.
- Frontend `chat-settings-sheet.tsx:723` then renders the warning whenever the slider exceeds that 4096 cap.

**On GB10 the warning is always wrong** — there's no separate VRAM, "system RAM" *is* GPU memory. KV for 32k ctx on a 27B GQA model is ~8 GB, which fits comfortably in actual unified-memory headroom even with the model loaded.

**The Q8 swap path proves this empirically:** loading UD-Q8_K_XL (35 GB) when free was higher gave us `max_available_ctx = 221440` automatically — the same code path produced a useful number when its inputs reflected reality. The moment-to-moment variance in `mem_get_info`'s "free" makes the Studio warning effectively non-deterministic on this box.

**Suggested runbook addition (`docs/GB10_UNSLOTH_SETUP.md` §5B or new "Known quirks" section):**

```markdown
### Studio's "Exceeds estimated VRAM" warning is cosmetic on GB10

When the chat-settings slider goes above 4096, the UI may flash:
  "Exceeds estimated VRAM capacity (4,096 tokens). The model may use
   system RAM."

Ignore it.  The estimator anchors to `torch.cuda.mem_get_info`'s "free"
field, which on Grace-Blackwell unified memory reflects a moment-in-time
CPU-RAM-style measurement that excludes reclaimable page cache.  Right
after loading a 50+ GB BF16 GGUF, "free" can drop near zero even though
100+ GB of unified pool is still available.  KV cache for a 32k context
on a 27B-class GQA model is ~8 GB — well within real headroom.  Drag the
slider to 32768 (or higher) freely.

If you want the suggestion auto-derived from real available memory,
`scripts/pi-launch.sh` prints a banner with `MemAvailable`, the loaded
variant, and a recommended ctx before exec'ing pi.
```

I would NOT patch the Studio frontend conditional (`ctxDisplayValue > ggufMaxContextLength`) from gx10 — that's upstream code, the fix should land in the unsloth-studio repo's UI, and the right test is "compare to total VRAM > 0 with hardware-aware unified-memory branch", not a one-liner. Worth a Studio-side bug report next time we have an extra cycle. Not blocking us tonight.

## 4. Variant auto-discovery — confirming the design intent

Your MIB §1 (and the architecture docs) treat variant choice as Studio-side, not pi-mono-side. Confirming that's still the right line: the `/api/inference/load` endpoint requires explicit `gguf_variant`; without it, the load path falls through to a transformers (non-GGUF) loader (`backend/routes/inference.py:430`). Pi-mono only ever sends the OpenAI-style `model: <repo_id>`, and Studio routes to whatever variant is currently loaded.

This means: **the only way to "auto-pick" a variant for pi-mono is at the Studio-load step, before pi sees anything.** The `studio-status.js` banner is the right place for that ergonomic — it surfaces the cached-vs-loaded mismatch at the moment a human is most likely to notice (right when launching pi). Auto-loading the largest cached variant on banner render felt like overreach for tonight (it's a non-trivial side effect; user might have intentionally chosen a smaller variant for speed). Easy to add later behind `STUDIO_AUTOLOAD=1` if you and Sergio agree the ergonomics are right.
